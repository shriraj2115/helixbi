# Day 1

## Goals
Fix the ESLint flat configuration issue left from Day 0, then implement Phase 1's core calculated fields engine: build a custom Pratt Parser (lexer → parser → AST → SQL compiler) in `@helixbi/engine`, create the calculated fields state management in `@helixbi/state`, wire the formula editor UI with live SQL preview and autocomplete into `apps/web`, and integrate with DuckDB WASM's view projection system.

## Work Done
- Fixed the ESLint flat configuration in `apps/web/eslint.config.js` that was blocking pre-commit hooks since Day 0.
- Implemented a full custom Pratt Parser pipeline in `@helixbi/engine`:
  - **Lexer** (`formula/lexer.ts`): Tokenizes formula expressions into NUMBER, COLUMN_REF (`[col]`), OPERATOR (+, -, *, /), PAREN, and FUNCTION tokens. Handles whitespace, string boundaries, and nested brackets.
  - **Parser** (`formula/parser.ts`): Recursive descent Pratt parser with operator precedence. Supports binary expressions, unary negation, grouped expressions, function calls (e.g., `ABS()`, `ROUND()`), and column references.
  - **AST** (`formula/ast.ts`): Typed AST node definitions — `NumberLiteral`, `ColumnRef`, `BinaryExpr`, `UnaryExpr`, `FunctionCall`.
  - **Compiler** (`formula/compiler.ts`): Walks the AST and compiles to DuckDB SQL expressions. `parseAndCompileFormula()` returns both the SQL string and extracted column dependencies.
- Created **View Compiler** (`formula/view.ts`): Generates `CREATE OR REPLACE VIEW` SQL that projects all physical columns plus computed calculated fields as additional columns.
- Built **Calculated Fields State** in `@helixbi/state`: Zustand store with `calculatedFields` array, `addCalculatedField()`, `removeCalculatedField()`, `updateCalculatedField()` actions using Immer middleware.
- Updated `apps/web/App.tsx` with:
  - Calculated Fields composer form with name input, formula expression input, output type selector.
  - Live SQL preview showing the compiled SQL as the user types.
  - Column autocomplete: typing `[` triggers a dropdown of available column names.
  - Name collision validation against existing CSV columns and other calculated fields.
  - DuckDB view projection rebuild on every calculated field add/remove.
- Added `apps/web/App.css` calculated field styling: form groups, SQL preview badges, autocomplete dropdown, column tags, delete buttons.
- Wrote 15 unit tests in `formula/formula.test.ts` testing arithmetic, nested expressions, column references, function calls, operator precedence, and error cases.
- Wrote 4 unit tests in `formula/view.test.ts` testing view SQL generation with 0, 1, and multiple calculated fields.
- All 19 tests passing under Vitest.

## Issues Faced
1. **ESLint Flat Config**: The `eslint.config.js` generated by Vite's template referenced `reactHooks.configs.flat.recommended` which was undefined in the installed package version.
2. **Pratt Parser Precedence**: Initial parser implementation didn't correctly handle `a + b * c` — multiplication wasn't binding tighter than addition.
3. **DuckDB View Column Conflicts**: When a calculated field name matched a physical column, `SELECT *, expr AS same_name` would fail in DuckDB.
4. **Autocomplete Cursor Position**: The `[` trigger for autocomplete needed to match at the end of the current expression without interfering with completed `[col]` references.

## Root Cause
1. The `eslint-plugin-react-hooks` package version resolved in the workspace had a different config structure than what the Vite template expected.
2. The Pratt parser's `getPrecedence()` function returned equal precedence for `+` and `*`.
3. DuckDB doesn't allow duplicate column names in a SELECT projection.
4. The regex for detecting in-progress column references was too greedy, matching already-closed brackets.

## Solutions Tried
1. Rewrote `eslint.config.js` to use the standard flat config format with explicit plugin registration and rule definitions.
2. Assigned correct Pratt precedence levels: `+`/`-` = 1, `*`/`/` = 2, unary = 3.
3. Added validation in `handleAddCalculatedField()` to reject names that collide with physical columns. The view compiler also handles graceful fallback.
4. Changed the regex to `\[([a-zA-Z0-9_]*)$` — only matches open brackets without closing brackets.

## Final Solution
All fixes applied successfully. ESLint pre-commit hooks re-enabled. Formula engine fully operational with 19 passing tests.

## Tradeoffs
- The Pratt parser is custom-built rather than using a library like `chevrotain` or `ohm-js` — this gives full control over error messages and SQL compilation but requires more maintenance.
- Column references use `[bracket]` syntax rather than backticks to avoid conflicts with SQL quoting conventions.

## Technical Debt
- The parser doesn't yet support string literals or comparison operators — only arithmetic and function calls.
- No dependency cycle detection in calculated fields (e.g., field A references field B which references field A).

## Risks
- Complex nested formulas with many function calls may produce deeply nested SQL that DuckDB's query planner handles less efficiently.

## Learnings
- Pratt parsing is elegant for expression grammars — the key insight is that each token's "binding power" determines how greedily it consumes operands from the right.
- DuckDB WASM's `CREATE OR REPLACE VIEW` is near-instant for computed projections, making it ideal for live formula preview.
- Zustand + Immer provides clean immutable state updates without Redux boilerplate.
